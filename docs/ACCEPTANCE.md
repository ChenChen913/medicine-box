## 0. 验收规则（先读这段，其余都是它的展开）

**两个轴，两个结论，二值，仅此而已：**

| 轴 | 结论取值 | 判定口径 |
| --- | --- | --- |
| **A 完成度** | `完成` / `未完成` | 轴 A 全部断言 = `是` → **完成**；任一 `否` → **未完成** |
| **B 达标度** | `达到` / `未达到` | 轴 B 全部断言 = `是` → **达到**；任一 `否` → **未达到** |

四条铁律：

1. **每条断言只有 `是` / `否`**。禁止出现"基本通过""80 分""大体达标""风险可控"这类模糊表述。
2. **`不适用` 不等于 `否`**。仅限标注 [条件] 的条目，且必须写明前提不成立的事实（例：未启用 Supabase，则 RLS 条目记 `不适用`）。不得用 `不适用` 逃避本该为 `否` 的条目。
3. **`待验证` 不是结论**。它是"尚未执行验证"的中间态，验收结束时不允许残留任何 `待验证`。
4. **发现 `否` → 先汇报 → 经老板批准 → 再修复 → 回归复测该条**。未经批准不得动手修复；修复后必须重跑该条的验证方法，并附证据。

**"完成"与"达到"互相独立**：可以有"功能做完了但没达标"，也可以有"代码质量达标但功能没做完"。最终交付状态 = 两个词并列给出。

## 1. 行业标准调研：这类项目通常被要求达到什么

以下 8 组是本项目所属类别（**个人/家庭向 Web 应用 · PWA · 前端存储 + 可选云后端 · 公网静态部署**）的通行要求，每条都给出可落地的硬指标。

### 1.1 需求与交付（Acceptance Criteria / Definition of Done）
- 验收标准必须**可测、二值、可复现**（Given–When–Then）；"做完"= 代码完成 + 评审通过 + 测试通过 + 文档同步 + 可部署。
- 交付物承诺必须与仓库实际一致（文档里写的脚本/文件必须在仓库中存在）。
- 来源：https://www.modernrequirements.com/glossary/acceptance-criteria/

### 1.2 Web 性能（Core Web Vitals，第 75 百分位、移动端）
- **LCP ≤ 2.5s**、**INP ≤ 200ms**、**CLS ≤ 0.1**（良好区间）——超出即为需改进/差。
- Lighthouse 四类审计（Performance / Accessibility / Best Practices / SEO）行业发布门槛通常取**各 ≥ 90**。
- 首屏主 JS chunk 体积应受控。**本项目采用业界通用的 gzip 传输体积口径：首屏 JS gzip ≤ 100 kB**
  （raw 体积仅作参考，不做硬门槛）。历史沿革：413KB → 189KB → 291.8 KiB → 238.5 KiB → 253.1 kB raw / 约 80 kB gzip。
  > 口径修订说明（2026-09-10，老板授权由 AI 决策）：原口径"raw ≤250KB"是自定数值。实测发现，
  > 若为凑够 raw 体积而把「需补货/用药记录」等底部导航直达的页面拆成按需加载，弱网下点页签需要等
  > 网络下载 —— 老板在真机上明确反馈"点击需补货加载很长时间"。经权衡，**导航即时响应优先于 raw 体积**，
  > 因此把这两个页面放回首屏，并把标准改为更贴近真实下载量的 gzip 口径（当前 80 kB，仍有充裕余量）。
- 来源：https://web.dev/articles/defining-core-web-vitals-thresholds

### 1.3 PWA 与可安装性
- 硬性前提：**HTTPS**（localhost 例外）。
- **manifest 必填**：name 或 short_name、icons（含 192×192 与 512×512）、start_url、display 为 standalone/fullscreen/minimal-ui。
- **离线能力**需 Service Worker 接管请求；无 SW 则"可安装"与"离线可用"是两件事。
- 来源：https://developer.mozilla.org/en-US/docs/Web/Progressive_web_apps/Guides/Making_PWAs_installable

### 1.4 无障碍（WCAG 2.2 AA）
- 四大原则：可感知 / 可操作 / 可理解 / 健壮。
- 2.2 版新增 A/AA 条款：**2.4.11 焦点不被遮挡**、**2.5.7 拖拽有非拖拽替代**、**2.5.8 目标尺寸 ≥ 24×24 CSS px**、**3.2.6 一致的帮助入口**、**3.3.7 不重复索取已填信息**、**3.3.8 可访问的身份认证**。
- 对比度：正文 ≥ 4.5:1，大字与 UI 组件 ≥ 3:1；键盘可达 + 焦点可见；页面不禁用缩放。
- 来源：https://www.equalweb.com/guides/wcag-checklist/

### 1.5 安全（OWASP Top 10:2025 + ASVS 5.0）
- **OWASP Top 10:2025**（2025-12 公布）中 **A01 存取控制失效（Broken Access Control）居首**；新版同时把**供应链失效**与**异常处理失当**这类条目推上台面。
  来源：https://www.twcert.org.tw/newepaper/cp-65-10556-3db82-3.html （官方完整十条见 https://owasp.org/Top10/ ，本次制定时网络受限未逐条抓取，执行验收时以官网复核为准）
- **OWASP ASVS 5.0** 的 L1/L2 是"有数据、无专职安全团队"项目的常用验证档位。
- 供应链：依赖锁定（lockfile 入库）、npm audit 无高危、CI 第三方 Action 固定版本。
- 密钥卫生：前端只能出现公开级密钥（Supabase anon key 属公开级）；service_role / PAT 绝不入库。

### 1.6 数据完整性与异常路径
- 备份/恢复必须**往返一致**（导出 → 清空 → 导入 → 逐字段比对）；导入文件是不可信输入，必须**逐字段清洗 + 版本校验**。
- 存储层必须有明确失败语义：**读失败 ≠ 空数据**、**写失败不得报成功**、配额满/隐私模式/损坏 JSON 都要有可见反馈。
- 日期一律按**本地时区**运算，禁止 toISOString().split('T')[0] 这类 UTC 泄漏（本项目历史教训见 docs/EXPERIENCE.md §3.3）。
- 并发：多标签页写入模型必须写明（本项目为 last-writer-wins，见 EXPERIENCE.md §10）。

### 1.7 健康类数据的隐私
- 数据最小化：家庭药箱属个人健康信息，**默认本地存储**是正确选择；启用云端必须配套访问隔离。
- 无第三方追踪/广告脚本；不把健康数据发给第三方。
- 应有"非医疗建议"性质的免责说明（用药提醒不得被当作医嘱）。

### 1.8 工程完备度
- 类型严格（strict 全开且 tsc --noEmit 零错误）、构建可重复（vite build 成功）。
- **存在自动化测试并在 CI 中执行**；发布前有冒烟基线（核心链路 + 控制台无 error/warn）。
- CI 覆盖：构建、部署、（缺此项即为否）测试门禁。
- 仓库元数据：LICENSE、依赖锁、Node 版本声明（engines/.nvmrc）、无死代码。
- 文档与代码一致：文档引用的每个脚本/文件都必须在仓库中存在。

## 2. 测试方法：把每条断言变成证据

"rubric 测试 / 对抗性测试 / 红蓝测试"在工程上的准确对应如下，本文件全部采用：

| 术语 | 本项目的落地方式 |
| --- | --- |
| **二值 rubric 测试** | 每条断言写成"前置条件 → 操作 → 期望结果"，跑一遍只回答 是/否（禁用打分制 rubric） |
| **静态门禁** | tsc --noEmit、vite build、npm audit、安全 grep（innerHTML / eval / dangerouslySetInnerHTML / 硬编码密钥） |
| **单元测试 + 属性测试** | 服务层（services/medicineService.ts）用 esbuild 打包 + mock localStorage 在 Node 跑；属性测试 = 随机操作序列后校验不变量恒成立 |
| **对抗性测试（adversarial）** | 主动用**恶意/极端输入与环境**打击系统假设（见 2.4 矩阵） |
| **红队 / 蓝队 / 紫队** | 红队模拟攻击者找突破口 → 蓝队加固修复 → 紫队把每次发现固化为回归用例（闭环，不允许"发现了但没留用例"） |
| **变异测试** | 在服务层注入人工缺陷（如把 >= 改成 >），看测试能否捕获；捕获率过低说明测试是摆设 |
| **时间旅行测试** | 注入假时钟，验证跨天/跨月/跨年/闰年/时区切换/系统时间回拨下的过期与统计正确性 |
| **状态污染测试** | 人为破坏 localStorage / 配额打满 / 隐私模式抛异常，验证降级与提示 |
| **跨端冒烟** | 桌面 1440 + 移动 390 两档，核心链路走通且 **console 无 error/warn**（本项目既有基线，见 EXPERIENCE.md §7.4） |

### 2.5 红蓝对抗清单（本项目攻击面）

**红队（找突破口）**：注入向量打药品名/备注/品牌 → 备份文件投毒（类型错乱、超深嵌套、危险 URL）→ 存储破坏（塞垃圾、打满配额）→ 供应链（依赖 typosquat、CI Action 未 pin）→ 越权（若启用 Supabase：anon key 直接读写全部数据）→ 社工（诱导导入他人备份）。
